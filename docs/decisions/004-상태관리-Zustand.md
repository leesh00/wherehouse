# 004. 상태관리로 Zustand 선택

- 날짜: 2026-11-10
- 상태: 확정

## 배경

등록·수정·목록·홈 네 화면이 같은 재고·위치 데이터를 본다. 등록 후 목록으로 돌아왔을 때 IndexedDB를 다시 읽지 않아도 최신 데이터가 보여야 한다.

상태 도구를 고르기 전에 **상태를 종류별로 나눴다.** 모든 상태를 전역 스토어에 넣지 않는 것이 핵심이다.

| 종류      | 예                                              | 둘 곳               | 이유                                                                                |
| --------- | ----------------------------------------------- | ------------------- | ----------------------------------------------------------------------------------- |
| 저장 상태 | 재고, 위치                                      | IndexedDB (원본)    | 새로고침·앱 재시작 후에도 남아야 함                                                 |
| 공유 상태 | 불러온 재고·위치 목록과 변경 함수               | Zustand 스토어      | 여러 화면이 같은 데이터를 봄. 저장 상태의 메모리 사본                               |
| URL 상태  | 지금 보는 위치(`?loc=`), 수정 중인 재고(`?id=`) | 쿼리 파라미터       | 새로고침·뒤로가기·링크 공유에도 유지. 정적 내보내기라 동적 경로 대신 쿼리 사용(003) |
| 화면 상태 | 폼 입력값, 저장 중 여부, 에러 메시지            | 컴포넌트 `useState` | 그 화면에서만 쓰고, 떠나면 버려도 됨                                                |

저장 흐름은 **화면 → 스토어 함수 → 어댑터 저장 → 성공 시 스토어 갱신**이다. 저장이 실패하면 스토어가 바뀌지 않으므로 화면과 DB가 어긋나지 않는다. 폼은 입력값을 유지한 채 에러를 보여준다.

## 선택지

| 선택지                   | 장점                                                                                                         | 단점                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| React Context + useState | 추가 패키지 없음                                                                                             | Provider 값이 바뀌면 그 아래 소비자가 모두 리렌더. 비동기 저장 로직을 둘 자리가 애매함 |
| Redux Toolkit            | 표준적, DevTools·미들웨어 풍부                                                                               | slice·store·Provider 설정이 이 규모에 비해 많음. 비동기는 thunk로 한 겹 더             |
| Zustand                  | 훅 하나(`create`)로 끝, Provider 불필요, 셀렉터로 필요한 값만 구독, 비동기 함수를 스토어에 바로 작성, 약 1KB | 구조를 강제하지 않아 규칙을 직접 정해야 함                                             |

## 결정

Zustand. 스토어는 `src/hooks/useInventory.ts` 하나이고, 담는 것은 `locations`, `items`, `loaded`와 `load`/`addItem`/`updateItem`뿐이다.

## 이유

- 공유 상태가 "재고·위치 목록" 하나뿐이라 Redux의 구조는 과하다.
- Context는 값이 바뀔 때마다 그 아래 소비자가 모두 리렌더된다. Zustand는 `useInventory((s) => s.items)`처럼 고른 값이 바뀔 때만 리렌더된다.
- 스토어 함수 안에서 `await adapter.addItem()` 후 `set()`을 하면 되므로 "성공 시에만 갱신" 흐름이 코드에 그대로 드러난다.
- Provider가 없어 정적 내보내기·Capacitor 환경과도 충돌이 없다.
- Zustand가 구조를 강제하지 않는 단점은 위 상태 분류표와 CLAUDE.md 규칙으로 보완한다.

## 구현하며 주의한 점

- Zustand v5에서 셀렉터가 매번 새 배열을 만들면(`s.locations.filter(...)`) 무한 렌더가 난다. 원본 배열을 고른 뒤 컴포넌트에서 거른다.
- 어댑터는 처음 쓸 때 연다(`adapter ??= createIdbAdapter()`). 빌드 시 프리렌더 환경에는 `indexedDB`가 없기 때문이다.
