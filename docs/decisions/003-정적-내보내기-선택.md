# 003. Next.js에서 SSR 대신 정적 내보내기(SSG) 선택

- 날짜: 2026-10-28
- 상태: 확정

## 배경

Next.js는 SSR, 서버 컴포넌트 데이터 패칭, API 라우트, 서버 액션 같은 서버 기능이 강점이다. 하지만 WhereHouse는 다음 조건을 가진다.

- 2차 이후 Capacitor로 Android 앱을 만든다. Capacitor는 빌드된 정적 파일(HTML/JS/CSS)을 앱 안에 넣어 WebView로 띄운다. 앱 안에는 Node.js 서버가 없다.
- 재고 데이터는 사용자 기기의 IndexedDB에 있다. 서버는 이 데이터에 접근할 수 없으니, 서버가 미리 그려줄 내용이 없다.
- 개인 재고 화면은 검색 엔진에 노출될 필요가 없다. SEO가 SSR의 큰 이유 중 하나인데 이 앱에는 해당하지 않는다.

"Next.js인데 왜 SSR을 안 썼나?"라는 질문에 대한 답은 이 세 가지다.

## 선택지

| 선택지                             | 장점                                                                     | 단점                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| SSR (기본 Next.js 서버)            | SEO, 첫 화면 데이터 포함, 서버 기능 사용 가능                            | Capacitor에 서버가 없어 앱에서 동작하지 않음. 데이터가 기기에 있어 SSR 이득이 없음. 서버 운영 비용 |
| 정적 내보내기 (`output: 'export'`) | 웹·앱이 같은 빌드 결과물 사용. 어떤 정적 호스팅에도 배포 가능, 비용 없음 | 동적 경로, API 라우트, 서버 액션, 이미지 최적화 사용 불가                                          |
| Vite + React (Next.js 미사용)      | 더 가볍고 단순함                                                         | 파일 기반 라우팅, 레이아웃 등 직접 구성 필요. 이후 웹 공개 페이지(소개 등)에 SSG 활용 여지 없음    |

## 결정

Next.js App Router + 정적 내보내기(`output: 'export'`, `trailingSlash: true`, `images.unoptimized: true`).

## 이유

- Capacitor 앱과 Vercel 웹이 같은 `out/` 결과물을 쓴다. 배포 대상이 늘어도 빌드는 하나다.
- 데이터가 클라이언트(IndexedDB)에만 있으므로 화면은 결국 브라우저에서 그려진다. SSR은 서버 비용만 늘린다.
- 제약에 맞춰 규칙을 정했다.
  - 동적 경로(`[id]`) 대신 쿼리 파라미터: `/item/edit?id=...`. 빌드 시점에 id를 알 수 없기 때문이다.
  - `useSearchParams`를 쓰는 컴포넌트는 Suspense로 감싼다. 정적 빌드 시 쿼리 값이 없어 그 부분은 클라이언트에서 렌더링된다.
  - `next/image`는 `unoptimized`로 쓴다. 기본 이미지 최적화는 서버가 필요하다.
- Next.js를 쓰는 이유는 SSR이 아니라 파일 기반 라우팅, 레이아웃, 빌드 최적화, 그리고 나중에 공개 페이지가 생기면 SSG로 쓸 수 있는 여지다.
