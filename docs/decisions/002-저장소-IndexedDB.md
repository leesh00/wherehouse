# 002. 저장소로 IndexedDB 선택

- 날짜: 2026-11-10
- 상태: 확정

## 배경

재고·위치 데이터를 저장할 곳이 필요하다. 조건은 다음과 같다.

- 1~2차는 무료 서비스만 쓰고, 서버 없이 동작해야 한다.
- 나중에 Capacitor 앱으로 옮겨도 같은 코드가 동작해야 한다.
- 서버 동기화를 붙이더라도 로컬 우선으로 설계한다.

## 선택지

| 선택지                          | 장점                                                                         | 단점                                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| localStorage                    | API가 가장 단순                                                              | 문자열만 저장(매번 JSON 직렬화), 용량 약 5MB, 동기 API라 메인 스레드를 막음, 인덱스·트랜잭션 없음 |
| IndexedDB (idb 래퍼)            | 객체를 그대로 저장, 대용량, 비동기, 트랜잭션·인덱스 지원, WebView에서도 동작 | 원본 API가 이벤트 기반이라 복잡함 → idb(약 1KB)로 Promise화                                       |
| 원격 DB (Supabase, Firebase 등) | 기기 간 동기화                                                               | 서버·계정 필요, 오프라인 약함, 무료 한도 관리 필요. 1차 범위 밖                                   |
| Capacitor SQLite                | 앱에서 성능 좋음                                                             | 웹(Vercel)에서는 쓸 수 없음. 1차는 웹 배포                                                        |

## 결정

IndexedDB + `idb` 라이브러리. 화면과 스토어는 `StorageAdapter` 인터페이스(`src/core/storage.ts`)로만 접근한다.

## 이유

- 웹과 Capacitor WebView 모두에서 별도 설정 없이 동작한다.
- 수정은 "읽고 → 합쳐서 → 쓰기"를 한 트랜잭션에서 처리할 수 있다(`updateItem`).
- 어댑터 인터페이스 뒤에 두었으므로 나중에 SQLite나 서버 동기화로 바꿔도 화면 코드는 바뀌지 않는다.
- 테스트는 `fake-indexeddb`를 쓴다. Node에서 실제 IndexedDB API 동작(새로고침 후 유지 포함)을 검증할 수 있다. 메모리 목(mock)으로는 실제 구현을 검증할 수 없다.
- 기본 위치(방, 부엌, 화장실)는 DB를 처음 만들 때(`upgrade`) 한 번만 넣는다. id는 고정값(`room`, `kitchen`, `bathroom`)이라 URL에 그대로 쓸 수 있다.
